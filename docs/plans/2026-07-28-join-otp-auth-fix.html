What was brokenThe login UI shipped; its backend never did.

The join panel POSTs to request-otp and verify-otp — no handler for either has ever existed in drop-reset-club. The only OTP backend lives in reset-site (2026.reset.club) and only covers the send half, with a different verify flow.

On top of that, a falsy-string bug (_opts.linkBase || …) made the apex fall back to the legacy /n path, whose 301 redirect downgrades the login POST into a GET.

Not a regression: nothing in the recent launch broke this — the flow never had a working backend on these domains.
The fixTwo native endpoints + a one-line frontend repair.
PieceWhat it does
request-otpChecks the contact is a known guest/profile/booking, then has Supabase send the SMS or email code. Unknown contacts are steered to Join.
verify-otpVerifies the code with Supabase, sets the standard reset_session cookie the site already trusts, returns the guest's first name.
join.jsHonors the empty-string link base so apex calls /api/auth directly — no more dead 301.

Logic lives in a shared module with vitest coverage, following the save/share endpoint pattern. No cross-worker proxying; no middleware changes needed — existing routing already forwards every path variant to the new endpoints.

Abuse control & rolloutZone rate limit + Supabase throttling; staging first.

The live Cloudflare rule (POST /api/*, 5 requests per 10 seconds per IP) plus Supabase's own OTP throttling cover abuse. No in-function rate limiter — in-memory counters don't survive serverless isolates.

Rollout: deploy to staging.reset.club, real phone login round-trip there, then promote to prod. Preview env needs the publishable Supabase key added; prod already has everything.
